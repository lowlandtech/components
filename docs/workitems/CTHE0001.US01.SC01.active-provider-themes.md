**Chosen surface.** The provider-scoped theme surface that Components already
owns in `src/lib/Theme` and `src/lib/ThemeProvider`: `IComponentTheme`,
`IComponentClassTheme`, `IComponentFragmentTheme`, `IThemeStyleFamily`,
`ComponentSlotKey`, `ThemeClassSlot`, `ThemeClassMergeMode`,
`IComponentThemeResolver` and `ComponentThemeService`, with `ThemeProvider` as
the boundary that renders `data-theme-provider`, `data-theme-name` and
`data-theme-style` and cascades `ThemeProviderContext`. The bridge projects
the theme of an active plugin owner onto those existing contracts, so a host
keeps resolving themes the way it does today and only the *owner* decides
whether a theme is selected.

**The gap the review named.** An installed theme is not proof of active
ownership. The resolver of the host finds a theme by its name, so the theme of
a plugin owner that withdrew stays reachable as long as a provider selects it.
The bridge closes that path: a provider only resolves the theme of an owner
that is active, and the withdrawal of an owner restores the host defaults of
the providers it had selected.

**Host authority.** The host owns which plugin owners are active and delivers
that authority to the bridge as a revision, exactly as the panel and the block
scope do. The bridge publishes the themes of the revision it holds and
projects the style family, the token set and the stylesheet selection of the
active owners.

**Planned Components-owned contracts** (namespace `LowlandTech.Components`, in
`src/blocks/Theme`, owned by the Blocks package):

- `ComponentThemeBinding(string OwnerKey, string ProviderId, string ThemeKey, IComponentTheme Theme, IReadOnlyList<string> Stylesheets)`
- `ComponentThemeOwnerSnapshot(long Revision, IReadOnlyCollection<string> ActiveOwnerKeys)`
- `ComponentThemeOwnerBridge` with
  `ComponentThemeOwnerBridge(ComponentThemeService, ComponentThemeOwnerSnapshot)`,
  `Publish(ComponentThemeBinding)`, `Deliver(ComponentThemeOwnerSnapshot)`,
  `Revision`, `Snapshot`, `IsOwnerActive(string)`, `Enumerate()`,
  `Select(string, string)` and `StylesheetsFor(string)`
- `ComponentThemeBindingValidation(ComponentThemeBinding Binding, bool IsValid, IReadOnlyList<ComponentThemeBindingError> Errors)`
- `ComponentThemeBindingError(ComponentThemeBindingErrorCode Code, string Subject, string Message)`
- `ComponentThemeBindingErrorCode` with the members `InactiveOwner`,
  `MissingThemeName`, `InvalidStyleFamily`, `UndefinedMergeMode`,
  `InvalidStylesheetPath` and `DuplicateBinding`

**The base packages stay unchanged.** The bridge lives in the Blocks package
and uses the theme contracts of the base package as they are:
`IComponentTheme` carries the tokens, `IComponentClassTheme` the class slots
and `IComponentFragmentTheme` the fragments. The public contracts of the base
packages are not changed by this scope, and the theme of a plugin owner reaches
the resolver as the ordinary theme of the host.

**Validate one binding before publication.** A binding is validated before it
is published, and a refused binding changes nothing — the published themes and
the provider selections stay exactly as they were:

- the owner of the binding is not active — `InactiveOwner`
- the theme has no name — `MissingThemeName`
- the style family of the theme is empty — `InvalidStyleFamily`
- a class slot uses a merge mode that does not exist — `UndefinedMergeMode`
- a stylesheet is not a local package CSS path — `InvalidStylesheetPath`
- another binding already claims the same provider and theme key — `DuplicateBinding`

The stylesheet rule follows the rule of the plugin catalog: a stylesheet is a
local `_content` package CSS path, without traversal, query string or
fragment.

**Only the selected provider changes.** A provider resolves the theme it
selected, and no other provider of the same host is touched. The resolver keeps
its current semantics: the class of the theme replaces, prepends or appends to
the default class of the component, and the class of the consumer and the class
of the design mode stay last, in that order.

**Host defaults stay available.** The host registers its own theme first, so
the fallback of the resolver is the host theme, exactly as it is today. When an
owner withdraws, the bridge restores the host default for every provider that
had selected a theme of that owner and detaches the stylesheet selection of
that boundary. The withdrawal never deletes a deployed file: the plugin
stylesheet stays in the published package, it is only no longer selected.

**Wiring.** The host selects the theme of a plugin owner through the bridge,
and the bridge holds the resolver of the host. The base DI-only mode keeps
registering the host themes directly and stays unchanged.

**Independent of the panel and block scopes.** The theme bridge carries its own
owner snapshot contract, so this scope stays deliverable on its own. The three
snapshots have the same shape; a host that already owns the panel authority of
`CPAN0001` or the block authority of `CBLK0001` maps one onto the other.

## Implementation boundary

Bridge Plugins theme identities to the actual Components resolver in an optional integration layer. Preserve the current non-plugin mode, provider state, consumer class/fragment precedence and theme-style family boundaries.

## Acceptance criteria

- [ ] UAC01: Given two independent ThemeProviders and an active theme plugin, when classes/fragments/style families resolve, only the selected provider changes and explicit consumer overrides retain their existing precedence.
- [ ] UAC02: Given an inactive or invalid theme binding, when theme enumeration/resolution occurs, it is excluded or rejected before publication without changing the current provider selections.
- [ ] UAC03: Given a selected plugin theme in a published package consumer, when its owner withdraws, subsequent renders restore host defaults and detach plugin stylesheet selection while unrelated provider state and already deployed public files remain intact.
