## Implementation

The implementation phase covered the smallest behavior the three criteria
assert:

- `src/core/` owns the shared component contracts: the startup binding, the
  startup registration, the trusted startup map, the feature manifest, the
  activation result and error types, and the activator itself. `src/core` keeps
  no host-framework dependency.
- `src/lib/ComponentsControlsStartup.cs` and `src/blocks/ComponentsBlocksStartup.cs`
  register the logical key each base library owns, so a feature can declare a
  logical dependency on it. `src/core/ComponentsCoreStartup.cs` does the same
  for the Core package. A base library registers a key only; it carries no
  manifest and stays an ordinary dependency.
- `src/features/LowlandTech.Components.Features.Session/` publishes the
  manifest and the startup binding of the opt-in feature. The package contains
  no component of its own: the session surface stays in the base Blocks
  package, and the feature package depends on it as an ordinary NuGet
  dependency.
- The activator is a pure decision. It reads the manifest, the startup map and
  the deployed feature keys, and reports the outcome; it never changes the
  host project, the deployment snapshot or the startup map.
- The trusted startup map carries the capabilities the host provides. A
  feature cannot activate in a host that does not provide a capability its
  installation unit requires, and the refusal is reported as
  `TargetCapabilitiesRequired` — the name the shared Plugins capability
  contract reports the same refusal with, so a host adapter maps one refusal
  onto the other without a second vocabulary. A manifest published for a
  target family Components does not activate for keeps its own refusal,
  `UnsupportedTarget`.

### Rework after the coordinator review of 2026-10-24

The coordinator rejected the first implementation because UAC03 rewrote the
manifest target to `backend` and then activated it. That proved the refusal of
a different manifest, not the refusal of the valid published Blazor feature in
a backend only host. The rework keeps the published manifest unchanged and
moves the premise to the host:

- the acceptance builds a real Git workspace with two explicit host profiles,
  a backend only host and a Blazor Server host, each with the literal project
  evidence the shared Plugins capability contract reads;
- the host capabilities are never declared by the fixture. The backend host
  provides `backend` and the Blazor host provides `blazor` and
  `blazor-server`, both derived by the shared contract;
- the same unchanged packed feature package is validated against both hosts:
  the backend only host refuses it with `TargetCapabilitiesRequired` naming
  the package and the `blazor` requirement, and the Blazor host accepts it.
  The refusal is therefore a property of the host, not of the artifact;
- the Components activation of the same unchanged manifest in the backend only
  host is refused with the same name, and the host project bytes, the
  deployment snapshot and the manifest are unchanged afterwards. The host
  projects carry an MSBuild target that writes a marker, and the marker never
  appears, because validating a package set never builds the host.

The already proven missing dependency and missing deployment cases, and all
three acceptance criteria, are preserved. No second plugin lifecycle was
created: the Plugins contract stays the authority for host capabilities and
package compatibility, and the Components activator consumes what it derives.

## Implementation boundary

Choose one small existing Components feature and declare its stable logical plugin key, versioned manifest, symbolic contribution identities, logical dependencies and trusted startup bindings in an opt-in package. Keep NuGet identity distinct. Do not make every base control a plugin.

The implementation owns the opt-in feature package with its published
manifest, the Components feature activation contracts and the startup
registration of the feature. It does not own the host-side projection of
active panels, blocks, themes or pages (CPAN0001, CBLK0001, CTHE0001,
CPGS0001), the Plugins runtime (the Plugins repository), the installation and
deployment adapters of a host (Plugins and Coder), or any change to the public
contracts of the base packages.

The projection of an installed manifest onto the Components activation
descriptor belongs to the host adapters, which map the parsed Plugins manifest
the host already owns. This scope publishes the manifest and the contracts; it
does not fork the Plugins manifest schema.
