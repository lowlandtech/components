## Outcome

Components hosts expose plugin pages and navigation only while their owner is active.

## Refinement

Triaged 2026-10-25 by the components lane under the released refinement phase
`components-CPGS0001-US01-SC01-refinement`. This pass refined the scope only:
it implemented no production behavior and no acceptance criterion executed.
The scope stays `backlog` until the coordinator releases the execution phase.

**Chosen surface.** The page surface Components already owns and the route and
page primitives the Plugins repository already publishes. Components owns the
`PluginPageAttribute` in `src/core/PluginPageAttribute.cs` and the trusted
startup component maps `ComponentsStartupMap` and `ComponentsStartupBinding`
in `src/core`. Plugins owns `PluginComponentCatalog`, `PluginPageCatalog`,
`PluginRouteHost`, `PluginPageMetadata`, `PluginPageDescriptor`,
`PluginPageNavigation` and the route gateway that authorizes a destination
before it renders. The adapter maps the pages of the owners that are active
onto those primitives, so a host keeps resolving routes the way it does today
and only the *owner* decides whether a page is offered.

**The gap the review named.** `src/app/App.razor` routes through a fixed
`AdditionalAssemblies` array. Membership in that array grants the route of
every page of the assembly, so the loaded assembly — not the owner — decides
whether a page is reachable, and a withdrawn owner keeps its navigation entry
and its direct route. The Plugins side already knows how to project the pages
of the active manifests and how to authorize a destination before it renders
anything. What is missing is the Components-owned mapping that hands the
gateway the explicit identities of the *active* owners only.

**Host authority.** The host owns which plugin owners are active and delivers
that authority to the bridge as a revision, exactly as the panel, the block and
the theme scope do. The bridge publishes the pages of the revision it holds,
and a withdrawal is delivered as the next revision. The bridge holds no
retained fragment, so it needs no subscriber contract: every lookup reads the
revision the bridge holds.

**Planned Components-owned contracts** (namespace
`LowlandTech.Components.Features.Pages`, in the optional feature package
`src/features/LowlandTech.Components.Features.Pages`):

- `ComponentPageBinding(string OwnerKey, string SymbolicIdentity, string RoutePath)`
- `ComponentPageOwnerSnapshot(long Revision, IReadOnlyCollection<string> ActiveOwnerKeys)`
- `ComponentPageOwnerBridge` with
  `ComponentPageOwnerBridge(ComponentsStartupMap, ComponentPageOwnerSnapshot, IEnumerable<string>)`,
  `Publish(ComponentPageBinding)`, `Deliver(ComponentPageOwnerSnapshot)`,
  `Revision`, `Snapshot`, `IsOwnerActive(string)`, `Enumerate()`,
  `Resolve(string)`, `Navigation()` and `PageCatalog()`
- `ComponentPageBindingValidation(ComponentPageBinding Binding, bool IsValid, IReadOnlyList<ComponentPageBindingError> Errors)`
- `ComponentPageBindingError(ComponentPageBindingErrorCode Code, string Subject, string Message)`
- `ComponentPageBindingErrorCode` with the members `DuplicateBinding`,
  `UnresolvedComponent`, `WrongComponentType`, `MissingPageMetadata`,
  `ConflictingRoutePath` and `ReservedHostRoute`
- `ComponentPageNavigationEntry(string RoutePath, string Label, string Icon, int Order, string? Group, string? SubGroup)`

**Where the adapter lives — decided 2026-10-25.** The adapter depends on the
Plugins route and page primitives, and the review asks for the base libraries to
stay ordinary dependencies with the activation-aware integration in an optional
adapter. The coordinator chose the optional feature package
`src/features/LowlandTech.Components.Features.Pages`, beside the existing
`src/features/LowlandTech.Components.Features.Session`, so the dependency graph
of `LowlandTech.Components.Core`, `LowlandTech.Components` and
`LowlandTech.Components.Blocks` does not change. The alternative — the Blocks
package, beside the panel, block and theme bridges — was not taken, because it
would give every consumer of the base packages the Plugins stack. The
acceptance inventory accepts both homes, because the contract accessor resolves
the documented names in either namespace; the execution phase uses the
namespace of the chosen package.

**The metadata is the attribute the page really carries.** The label, the icon,
the order, the group, the subgroup and the navigation visibility come from the
`PluginPageAttribute` of the component the trusted startup map resolves, and
not from a value the host invented. A component that carries no such attribute
is not a page and is refused by name as `MissingPageMetadata`. The adapted
metadata is handed to the Plugins primitives as `PluginPageMetadata`, so the
Plugins repository keeps owning the metadata shape and Components does not
duplicate it.

**The host routes stay reserved.** The host names the routes it owns; a page
that claims one of them is refused by name as `ReservedHostRoute`. The refusal
never replaces the published projection: the previously valid page keeps its
route, its navigation entry and its page catalog entry, exactly as they were.

**The validation gates the candidate, the owner activity gates the
projection.** A page of an owner that is not active is a valid candidate, but it
is not published, not routable and not in the page catalog. That keeps the
withdrawal reversible: the next revision that names the owner active publishes
the page again without a new registration.

**A hidden page stays routable.** `ShowInNav = false` removes the page from
the navigation only. Its route still resolves, because the navigation and the
route are two different decisions, and a page that hides itself is still a page.

**The consumer proof.** The browser half of UAC03 runs in a separate
Interactive Server RCL consumer that restores the Components packages from an
offline feed, exactly as the consumer proofs of `CPAN0001` and `CTHE0001` do.
It serves a reserved host route of its own and a plugin page of an active
owner through the Plugins route gateway, withdraws the owner and proves that
the navigation entry is gone, that the retained URL of the page is denied or
reaches the host fallback, that a guarded page still authorizes its server
action before it renders content and that the reserved host route stays
available. The consumer proof belongs to the execution phase, where the
consumer harness is created.

**Acceptance inventory.** `src/test/CPGS0001.Integration/US01.ActivePluginPages/`:
one expression-bodied Shouldly Fact per UAC in `SC01_ActivePluginPages.cs`, the
contract accessor `ComponentsPageOwnerContracts.cs` and the page fixtures
`FakePluginPage.cs`, `FakeHiddenPluginPage.cs` and
`FakeUndescribedPluginPage.cs`. The accessor reaches the planned contracts by
their documented names and fails with the exact missing contract name, so an
unimplemented contract can never turn into a silent pass. The fixtures carry
the real `PluginPageAttribute` of Components, so the acceptance proves the
adapter against the metadata a plugin really declares. The browser half of
UAC03 is in
`src/e2e/CPGS0001.Integration/US01.ActivePluginPages/SC01_ActivePluginPagesE2E.cs`
and is skipped with the consumer and the bridge it still owes.

## Implementation boundary

Use existing Plugins route/page primitives and trusted startup component maps. Preserve base app routes. Adapt real PluginPage metadata without treating a loaded assembly or AdditionalAssemblies membership as authorization.

## Acceptance criteria

- [ ] UAC01: Given a deployed active page with metadata, when navigation and direct routing are evaluated, label/group/order/hidden-navigation behavior is preserved and host authorization runs before protected content/actions.
- [ ] UAC02: Given conflicting routes or invalid component metadata, when activation is validated, it fails by name before replacing the previously valid route/navigation projection.
- [ ] UAC03: Given a discovered page and retained URL, when its owner withdraws, subsequent navigation and direct route resolution are denied or reach host fallback; a stale browser projection cannot authorize server data/actions.

## Consumer integration boundary

Coder M6-011 consumes this page adapter through the shell route gateway. Expose
trusted metadata/registration without a dependency on Coder or the demo Router.
Verify an Interactive Server RCL consumer, including reserved host routes and
guarded retained URLs. WASM projection remains a separate integration mode.
