## Outcome

A person runs a declared action on a rendered document: one request carries the head and the
source/edge/target triple with its inputs, and the response's result cases and authoritative
document update the region — applied, refused or conflicted — without a re-read and without page
code.

## Refinement decisions (2026-11-26)

- **Transport is a host-supplied contract**, `ITransitionClient` in `src/core`, passed as a
  component parameter (so bUnit and the app use the same surface):
  `Task<TransitionResult> ApplyAsync(TransitionRequest request, CancellationToken ct = default)`.
  Components ships no HTTP client and no address.
- **The request is explicit**: `Head`, `SourceId`, `EdgeKey`, `TargetType`, `Inputs`
  (field -> value), `Properties` and `Edges` for a document write. The head is always sent.
- **The host owns the parse, the trigger owns the outcome**: `TransitionResult.Document` stays
  opaque, so the trigger raises `OnResult` and the host resolves the new snapshot and passes it
  back to `DocumentView`. Components never learns the document's storage shape.
- **Conflict is shown, never hidden**: the response's document is the host's to parse and pass
  back, the trigger clears the stale result and keeps the action inputs so the offered `retry`
  re-runs from the new head. It never keeps or displays a copy of the document itself.
- **Contract extension**: `DocumentAction.TargetType` was added so a creating transition can name
  its target type; the document view ignores it and only the trigger sends it.
- **Accessibility is part of the contract**: the result region is `role="status"` with
  `aria-live="polite"`, focus moves to it when a result arrives, and the outcome text is inside it.
- **Blocker, recorded rather than worked around**: the real transport needs Graph's HTTP
  transition entry (today only the MCP `session` tool runs transitions, handoff
  `20261126T082327906745Z-57c02c4e@components`). bUnit proves the behavior against a fake client;
  the deployed path is graph's own acceptance.

## What changes

| Surface | Change |
|---|---|
| `TransitionRequest`, `ITransitionClient` (`src/core/Transitions`) | the request envelope and the host contract, beside the delivered `TransitionResult` |
| `TransitionTrigger` (`src/lib/TransitionTrigger`) | the behavior and component: idle/submitting/refused/conflict/applied, the request build, the result region, focus and announcement |
| `DocumentView` | an action template and a result slot so a trigger composes inside the document region |

## Acceptance criteria

- [x] UAC01: Given a declared action and its inputs, when a person runs it, then one request carries the head, source id, edge key, target type and every input value.
- [x] UAC02: Given an applied result, when the response returns, then the region shows the returned cases and the host's new snapshot, and no re-read is requested.
- [x] UAC03: Given a refused result, when the response returns, then the cases render against the current document and no value was written.
- [x] UAC04: Given a conflict, when the response returns, then the response's document becomes the shown one, its inputs are the shown values, and the offered retry re-runs from the new head.
- [x] UAC05: Given a result arriving for a keyboard user, when it renders, then focus is on the result region and the outcome is announced through the polite live region.
- [x] UAC06: Given no client supplied, when an action is offered, then the trigger refuses with one diagnostic instead of failing silently.
- [x] UAC07: Given the submitting state, when the request is in flight, then the action is disabled and a second activation cannot send a second request.

## Boundaries

- No HTTP, no auth, no Graph address in the library; the host supplies the client and resolves the
  document.
- No optimistic UI: the region shows the returned state, not a guess.
- The trigger does not own the document's schema, validation or labels; it renders the result
  cases through `TransitionResultView`.
