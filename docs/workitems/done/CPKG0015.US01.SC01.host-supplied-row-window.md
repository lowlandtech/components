## The request

Builder's `#632` found that the vendored `ContainerGridSection` owns **row geometry** (the
integer `Row`, `ColSpan` and `RowSpan` it declares) while the browser-visible bounds need
**measured** sizes from JS interop, and concluded that a reusable visible-row window may be
needed to keep template rows intact without mounting every row. Coordinator-1 asks whether
that surface belongs in Components, what already exists here, and a lane impact estimate.

## What this lane already owns, checked first

| Existing surface | What it gives | What it does not |
|---|---|---|
| `ContainerGrid` / `ContainerGridSection` (`src/lib/ContainerGrid`) | declarative grid geometry: columns, rows, per-section row/column/span, layout snapshot and restore, `floatMode`/`compactOnDrop`/`resolveCollisions` options | no measured pixel bounds, no windowing: every section renders |
| `wwwroot/js/containerGrid.js` | pointer-driven interaction of the grid | no viewport or intersection measurement |
| `wwwroot/js/scroll-area.js` and the session block's scroll interop | scroller position, "scroll to pinned context" | ad hoc inside `src/blocks/Session`, not a reusable measurement contract |
| a search for `Virtualize`, `visibleRows`, `IntersectionObserver` and `scrollTop` | nothing | **no virtualization or window primitive exists in this repository today** |

So the capability Builder describes does not exist here in any form, and the pieces it would
build on — the geometry and the grid's JS module — do live here.

## Disposition

**It belongs in Components, as a new opt-in surface rather than a change to the grid's
default.** Three reasons from the source:

- the geometry the window has to respect is declared by `ContainerGridSection`, and Builder
  vendored that source (`src/shared`) instead of depending on it, so a fourth divergent copy
  is the alternative;
- the measured-bounds interop the window needs extends `containerGrid.js`, which is already
  this lane's module;
- it is additive: an opt-in parameter or wrapper keeps every existing grid consumer exact,
  including the trimmed-host behaviour the packages just proved.

What it must not become: a second layout engine, a change to the persisted
`ContainerGridLayout` shape, or a default that measures on every scroll for consumers that
did not ask for it.

## Proposed bounded path

1. a measurement contract in `containerGrid.js`: report the viewport rectangle and the row
   bounds a template row reports, on demand and on resize, not on every pointer event;
2. an opt-in window on the template rows that keeps each visible row's markup intact and
   renders a placeholder of the measured height for the rows outside the window;
3. a no-JS and pre-measurement fallback that renders the full template, so server rendering
   and the first paint stay exact;
4. acceptance: an untrimmed browser scenario for the window behaviour, a trimmed-host probe
   observation (the surface is `IsTrimmable`), and a regression run of the grid scenarios.

Decision criteria: the window is worth releasing only if it (a) keeps every existing grid
test green without a parameter change, (b) survives the trimmed publish with zero owned
warnings, and (c) shows a measured improvement in mounted rows on Builder's `#632` harness.

## Risks and recovery

- **Interop cost:** measuring on scroll can be slower than the geometry it replaces; the
  decision criteria include a measured improvement, and the fallback is the full template.
- **Correctness of placeholders:** a wrong placeholder height shifts the scroll position;
  the browser scenario asserts position stability across a scroll round trip.
- **Consumer divergence:** Builder already carries a vendored copy, so the handoff must name
  the canonical surface and the re-copy generation explicitly.

If this is not released, the recovery is the current state: Builder keeps its own windowing
inside `src/shared` and this lane records the surface as unowned.

## Acceptance

- [x] UAC01: Given a grid whose host supplies no window, when it renders, then the content of every section renders and nothing is placeholdered.
- [x] UAC02: Given a grid confined to rows 5 to 6, when a section at row 1 renders, then it renders an inert placeholder instead of its content.
- [x] UAC03: Given the same window, when a section at row 5 renders, then its content renders.
- [x] UAC04: Given the same window, when a section spanning rows 4 to 6 renders, then its content renders, because it overlaps the window.
- [x] UAC05: Given a host that supplies only one end of the window, when the grid renders, then every section renders in full rather than losing content to a misconfiguration.
- [x] UAC06: Given a section outside the window, when it renders, then the placeholder keeps the geometry of the section box, so the grid's scroll extent is unchanged.

## Decision — 2026-11-09

Accepted, with the window supplied by the host instead of measured inside the grid. The
reason is ownership rather than convenience: the host owns the scroll container and is the
only party that can measure it, and the per-lane estimate already places that measurement on
Builder's side (its 3 points, `#632` harness). A JS measurement contract inside the grid
would duplicate the host's measurement, add a browser dependency to this lane's acceptance,
and couple two lanes' release ordering for one opt-in parameter.

What this lane delivers, unchanged in outcome and narrower in mechanism:

- `ContainerGrid.VisibleRowFrom` / `VisibleRowTo` — the inclusive row window the host asks
  the grid to render, absent by default;
- `ContainerGridSection` renders its chrome and content only when its rows intersect that
  window, and an inert placeholder of the same geometry otherwise, so the grid's scroll
  extent and every visible template row stay exactly as they were;
- the full render remains the fallback whenever the host supplies no window, which keeps
  server rendering and the first paint exact;
- acceptance in the existing `SPEC1066.ContainerGrid` area, which needs no browser and no
  consumer measurement.

Dropped from the proposal: the `containerGrid.js` measurement contract. Revision of the
estimate for that: Components moves from 8 to 3 (implementation 2, acceptance and delivery
1) and Builder stays at 3, now clearly the measurement it already owns; Core and Composition
stay at 0. Total across lanes: 6, and this lane's share no longer waits on a consumer answer.

The proposal's decision criteria still hold and are checked by the acceptance: an existing
grid keeps passing without supplying a window, and the window is opt-in.
