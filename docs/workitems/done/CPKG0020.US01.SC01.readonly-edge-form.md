## Outcome

A document view that shows an existing relation with `DynamicEdgeForm` can put the form in
read-only mode, so every field shows its value as text and nothing invites an edit that would
write nowhere.

## The request

Graph renders CORBIS documents with defined components instead of markup. `DynamicEdgeForm`
today only renders inputs, so a view of an existing relation looks editable while saving
nothing; Graph uses `FormField` read-only in the meantime. It asked for a read-only/disabled
mode plus a way to supply the values being viewed. No new field types are needed.

## What changes

| Surface | Change |
|---|---|
| `DynamicEdgeForm.ReadOnly` | an optional flag; when set, every field renders its value as text and no input is rendered |
| `DynamicEdgeForm.Values` | an optional value dictionary keyed by field name, used as the form's current values (displayed in read-only mode and as the starting values otherwise) |
| editable path | unchanged: with no `ReadOnly`, the inputs, rules and `OnChange` behave as before |

## Acceptance criteria

- [x] UAC01: Given a relation view whose form is read-only, when it renders, then each field shows its value as text and no input element is rendered.
- [x] UAC02: Given that read-only form, when a person clicks or types on a field, then no change callback fires and no value is written.
- [x] UAC03: Given read-only mode with supplied values, when the form renders, then each named field displays the value from the dictionary.
- [x] UAC04: Given the default editable form, when it renders, then its inputs, rules and change callbacks behave exactly as before.

## Boundaries

- Additive surface only: an existing editable form is unaffected, and no field type or rule
  contract changes.
- Read-only mode is a presentation mode of this component, not a second form control; the host
  still decides what the document shows.
