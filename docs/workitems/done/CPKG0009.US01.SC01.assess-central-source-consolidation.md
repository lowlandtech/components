## Option-by-option impact

### A — Core becomes the sole central source

- **Package pins:** the contracts identity `LowlandTech.Components.Core` moves to Core.
  Every consumer that pins it (Core's own closure, Coder, Builder, Backend, Tinytools)
  re-points, and this lane's four packages take a Core-owned contracts pin instead of
  producing one.
- **Producer:** this lane stops producing a package, so `docs/core.md`'s direction
  ("Components owns LowlandTech.Components.Core") is inverted.
- **Release:** one train instead of two aligned trains. The cycle disappears, which is
  the benefit; the cost is that every components change rides the Core cadence.
- **Estimate:** **13** points. Assumption: Core absorbs the contracts package unchanged
  and keeps the trim annotations; the estimate grows if the IsTrimmable metadata and the
  two member declarations have to be re-established in a new producer.

### B — Plugins becomes the sole central source

- **Package pins:** this lane would gain a Plugins-owned contracts pin while it already
  consumes `LowlandTech.Plugins.Domain` in `Features.Pages`, so one upstream becomes two
  and the exact-pin surface widens rather than narrows.
- **Producer:** same loss of the contracts producer as A, with an upstream that is not in
  the current dependency direction of the two base packages.
- **Release:** three-way alignment (Core, Plugins, this lane) instead of two-way.
- **Estimate:** **21** points. Assumption: Plugins publishes a contracts package it does
  not publish today and keeps its current package set otherwise.

### C — Backend-only Core plus browser-only Core.Frontend, Plugins retains its API/App/product packages

- **Package pins:** the base packages keep their identity. `.Components`, `.Blocks` and
  the two feature packages gain a second exact upstream (`Core.Frontend`) because they
  are browser-facing, while `LowlandTech.Components.Core` stays Components-owned and
  Core-facing. Our batch would carry two exact pins instead of one.
- **Producer:** unchanged. This is the only option of the four that leaves this lane's
  producer role intact.
- **Release:** the cost is a second alignment axis per batch (~2–3 minutes more per
  publication at the measured cost, plus one more version to watch), and a consumer that
  resolves the browser packages must resolve Core.Frontend as well.
- **Estimate:** **5** points. Assumption: Core.Frontend ships the same contract surface
  the frontend packages use today; +3 points if it introduces abstractions that the
  components must implement.

### D — Reference: move the repository wholesale into the central source

- **Package pins:** the same five identities survive but every consumer re-points at
  once, and the issue mirror, the roadmap and the six accepted scopes travel.
- **Release:** one train, one CI, one board; the cycle disappears.
- **Estimate:** **34** points. Assumption: the 2,399-test suite, the Pages deployment and
  the six accepted scopes move without re-acceptance; a re-acceptance of the six scopes
  would exceed the scale.

## Disposition

- **Option C is the no-impact case for the Components package identity.** This lane keeps
  producing its five packages and keeps `LowlandTech.Components.Core`; the change it
  absorbs is a second exact upstream on the browser-facing packages.
- **Options A and B are not no-impact.** Both remove this lane's producer role, and B also
  widens the exact-pin surface.
- **Lane view on cost:** C (5) is the cheapest that keeps one producer per package; D (34)
  buys the same de-coupling for seven times the cost; A (13) and B (21) buy it by deleting
  the boundary that keeps the trim contract and the design contracts in this repository.

Cadence assumption for every estimate: an hourly lane, one publication per Core
generation, and one consumer re-pin notification per affected lane.
