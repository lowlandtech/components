# CPKG0017-US01-SC01 — Keep the packaging harness on the target framework band

## Outcome

The packaging scenario carries the framework packages of the band this repository targets and
refuses to substitute another one, so Components cannot silently resolve to a newer .NET just
because a newer runtime happens to be installed on the machine.

## The drift

Every project of this repository targets `net10.0`, and the published packages ship
`lib/net10.0` only. The packaging scenario nevertheless resolved its framework version as the
**highest installed** ASP.NET runtime:

```powershell
$sorted = $versions | Sort-Object -Property @{ Expression = { [version](($_ -split '-')[0]) } }
return @($sorted)[-1]
```

On this machine the installed ASP.NET runtimes are `8.0.34`, `9.0.23`, `10.0.15` **and
`11.0.0`**, so the scenario resolved `11.0.0`, required
`Microsoft.AspNetCore.App.Internal.Assets/11.0.0` from the NuGet cache — which holds no such
package — and failed before exercising anything:

```
The framework package Microsoft.AspNetCore.App.Internal.Assets 11.0.0 is not in the global cache.
```

Both packaging scopes (`CPKG0001`, `CPKG0002`) turned red for that reason alone: 7 failures in a
2,412-test run, none of them related to a component change.

## What changes

| Surface | Change |
|---|---|
| `Get-TargetFrameworkBand` (new) | reads the target framework of the package under test and returns it as `major.minor`; a framework that is not `net<major>.<minor>` is refused by name |
| `Get-AspNetCoreRuntimeVersion` | takes that band and returns the highest installed runtime **within it**; when the band has no installed runtime it refuses with the band and the installed versions in the message |
| the call site | resolves the band once and passes it in, so there is no path that picks a version without naming the band it belongs to |

## Acceptance

- [x] UAC01: Given projects that target `net10.0` and installed runtimes of several major versions, when the scenario resolves its framework packages, then it resolves the `10.0` band and not the highest runtime.
- [x] UAC02: Given a target band with no installed runtime of that band, when the scenario resolves, then it refuses with a named diagnostic that states the band and the installed versions, instead of substituting another framework.
- [x] UAC03: Given the fix, when the two packaging scopes run, then both pass.
- [x] UAC04: Given the fix, when the whole suite runs, then no test fails.

## Boundaries

- This repairs test infrastructure: no package code, no published contract and no target
  framework changes. `net10.0` stays the repository's framework, which is what keeps the
  package itself off .NET 11.
- The SDK itself is a machine matter: only `11.0.100` is installed here, so the repository
  cannot pin an SDK to 10 without one being installed. That is reported, not worked around.
- The completed `CPKG0001`'s acceptance and evidence stay as they are; this scope owns the
  repair of its harness.

### The SDK, stated rather than worked around

The framework *packages* are now resolved on the band the repository targets, which is the
part that was actually adopting .NET 11. The SDK is a separate matter: only `11.0.100` is
installed here, so a `global.json` pinning a `10.0` SDK would stop every build in this
repository until a .NET 10 SDK is installed. That pin is therefore not added; installing the
SDK is a machine decision, and the pin is a one-file change once it exists.
