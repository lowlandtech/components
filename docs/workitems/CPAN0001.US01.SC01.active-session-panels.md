## Outcome

Components consumers render session panels only for active plugin owners through a reusable optional bridge.

## Refinement

Triaged 2026-10-24 by the components lane under the released refinement phase
`components-CPAN0001-US01-SC01-refinement`. This pass refined the scope only:
it implemented no production behavior and no acceptance criterion executed.
The scope stays `backlog` until the coordinator releases the execution phase.

**Chosen surface.** The session plugin surface that Components already owns in
`src/blocks/Session`: `ISessionPlugin`, `SessionPluginDescriptor`,
`SessionPluginContext`, `ISessionPluginRegistry`, the default
`SessionPluginRegistry` and the `SessionPluginHost` component. The bridge
projects the plugin owners that are active onto those existing contracts, so a
host keeps rendering panels the way it does today and only the *owner* decides
whether a panel is projected.

**Host authority.** The host owns which plugin owners are active and delivers
that authority to the bridge as a revision. The bridge projects the owners of
the revision it holds; a withdrawal is delivered as the next revision, and a
stale callback rechecks the authority before it acts.

**Planned Components-owned contracts** (namespace `LowlandTech.Components`, in
`src/blocks/Session`):

- `SessionPluginOwnerSnapshot(long Revision, IReadOnlyCollection<string> ActiveOwnerKeys)`
- `SessionPluginOwnerBridge` with
  `SessionPluginOwnerBridge(SessionPluginOwnerSnapshot, IEnumerable<ISessionPlugin>, ISessionPluginSettingsStore?)`,
  `Register(string ownerKey, ISessionPlugin plugin)`,
  `Deliver(SessionPluginOwnerSnapshot)`, `Subscribe(Action<long> onRevision)`,
  `Revision`, `Snapshot`, `IsOwnerActive(string ownerKey)` and the
  `ISessionPluginRegistry` members `GetAllPlugins()` and `ListAsync`.

**Placement parameterization.** `SessionPluginHost` currently always selects
`SessionPluginPlacement.RightSidebar`. The host must expose the placement as a
parameter with the right sidebar as its default, so a host can select its own
placement while the existing stable slots — `RightSidebar`, `WorkspaceTab` and
`FooterTool` — stay unchanged and no new slot is introduced.

**Existing semantics stay intact.** The base DI-only mode keeps working: a host
that registers no bridge still resolves the default registry over the plain
`ISessionPlugin` instances. The bridged panels reuse the existing rules of the
registry: the persisted enablement hides a panel, a protected descriptor stays
visible against that persisted enablement, the persisted order wins over the
descriptor order, the badge is only reported for a visible panel, and the
`OnReloadRequested` callback still reaches the host. A protected descriptor
protects a panel against the persisted enablement only; it never survives the
deactivation of its owner, and a reactivation never erases the persisted
preferences.

**Acceptance inventory.** `src/test/CPAN0001.Integration/US01.SessionPanels/`:
one expression-bodied Shouldly Fact per UAC in `SC01_ActiveSessionPanels.cs`,
the arrange fixtures `FakeSessionPlugin.cs` and
`FakeSessionPluginSettingsStore.cs`, and the contract accessor
`ComponentsPluginOwnerContracts.cs`. The accessor reaches the planned bridge
contracts by their documented names and fails with the exact missing contract
name, so an unimplemented contract can never turn into a silent pass. The Facts
arrange the owners, the placements, the persisted enablement and order and two
live consumers against the existing `ISessionPlugin` contracts, and they render
the real `SessionPluginHost` through bUnit.

Every Fact is skipped and names its missing dependency:

- UAC01 — the plugin owner bridge and the placement parameter of the session
  plugin host do not exist yet, so no owner can be projected onto the session
  panel contracts.
- UAC02 — the plugin owner bridge does not exist yet, so the bridged panels do
  not retain the enablement, order, badge and callback semantics of the
  existing registry.
- UAC03 — the plugin owner bridge does not deliver revisions or admit
  subscribers yet, so a withdrawal cannot clear a retained fragment in two live
  consumers.

**No browser scenario in this scope's inventory.** The browser proof of this
scope is the separate Interactive Server RCL consumer with two circuits that
the consumer integration boundary names; that consumer does not exist yet, and

**External prerequisite.** The Plugins prerequisite of this scope,

## Implementation boundary

Map validated plugin ownership to existing ISessionPlugin contracts; preserve the base DI-only mode. Parameterize the host placement instead of always selecting RightSidebar. Expose the reusable bridge for Coder.Shell rather than copying Components internals into Coder.

The execution phase owns the plugin owner bridge, the owner snapshot and the
placement parameter of the session plugin host. It does not own the Plugins
runtime (the Plugins repository), the installation and deployment adapters of a
host (Plugins and Coder), the block, theme and page projections (CBLK0001,
CTHE0001, CPGS0001), or any change to the public contracts of the base
packages.

## Acceptance criteria

- [x] UAC01: Given active/inactive panel owners at RightSidebar, WorkspaceTab and FooterTool, when a host queries and renders its selected placement, only the active matching panels appear in both ListAsync and GetAllPlugins paths with existing stable slots.
- [x] UAC02: Given persisted enablement/order and protected/order-locked descriptors, when settings change, badges, visibility, callbacks and ordering retain existing semantics; a protected setting cannot override workspace deactivation and reactivation does not erase preferences.
- [x] UAC03: Given two live consumers and a retained selected fragment, when the owner withdraws, both clear the fragment on the next delivered revision/render and show the host fallback; stale callbacks recheck host authority and no handler is newly admitted. Already admitted work may finish.

**The two defects the acceptance found.** The first execution of the
acceptance failed, and both failures were real:

- a panel that asks the host for a reload while the host is loading started

  died. `SessionPluginHost` now refuses to start a load while one is running,
  so a panel that asks for a reload during the load does not restart it.
- the bridge ignored a delivered revision that was not newer than the one it
  held, so a withdrawal that arrived with an older revision never took effect
  and a protected panel survived the deactivation of its owner. The bridge now
  projects the revision the host delivers, and the host owns the revision.

**The two defects the consumer proof found.** Both were real, and neither was
visible to the bUnit acceptance:

- the consumer did not make the host read the registry again. A re-render of
  the parent with unchanged parameters does not re-parameterize the child, so
  the session plugin host kept the panels of the withdrawn owner although the
  bridge had already dropped them. The consumer now carries the revision of
  the authority in the parameters of the host, which is the contract the host
  component implements.
- the first run of the consumer proof would have been a false pass. The empty
  state appeared because the interactive circuit of the consumer only started
  after the withdrawal, not because the withdrawal was delivered to it. The
  bridge admits no handler while no owner is active, so a circuit that is not
  live yet never hears a withdrawal. The consumer renders a marker once its
  circuit is live, and the browser scenario waits for that marker on both
  circuits before the withdrawal.
