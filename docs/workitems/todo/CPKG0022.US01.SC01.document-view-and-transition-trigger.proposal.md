## Outcome and scope

Two connected Components surfaces, so a host renders a CORBIS document and acts on it without
hand-written markup or a bespoke request handler:

1. **A document view.** One component takes a document contract — type, declared properties with
   their value kinds, values, relations, causal head and the actions it offers — and renders it
   generically. It replaces per-page record markup and the app-side "emit a model so the form has
   something to reflect" shim.
2. **A transition trigger.** A declarative trigger (`data-transition` plus its inputs) submits a
   source/edge/target triple to the host's transition client, and the response — outcome, result
   cases, authoritative document and head — updates the document region. One generic handler; no
   per-page code.

Both lean on the already-delivered pieces: `DataForm.Fields`/`Values` (`CPKG0019`),
`DynamicEdgeForm.ReadOnly`/`Values` (`CPKG0020`) and `TransitionResult`/`TransitionResultView`
(`CPKG0021`, issue #45).

This proposal authorizes refinement and materialization only. Implementation begins in the
linked slices below.

## Contract boundaries

- Components stays domain-agnostic: it owns `DocumentSnapshot` (the rendering contract),
  `TransitionRequest`/`TransitionResult` (the action contract) and the components that use them.
  No CORBIS, Graph or runner types enter the library; the host maps its payloads onto these
  records.
- The document payload stays data: the library renders what the contract declares and never
  discovers fields by reflection or models the document's storage.
- **No HTML or CSS fragments travel in transition data** (decided 2026-11-26). Result cases are
  structured JSON keyed by a stable code; wording is message keys resolved by the client; a
  server-rendered fragment is a later projection for non-Blazor consumers, not the contract.
- Validation is a sandbox: it returns outcome, cases and the evidence it observed, and never a
  document. Execution returns the authoritative document and head for applied, refused and
  conflict.
- The trigger is transport-agnostic: the host injects a `TransitionClient` delegate. Components
  ships no HTTP client and no Graph address.
- No new project, package or service: `src/core`, `src/lib`, `src/test` only.
- Labels are never raw keys in the UI: the document definition carries display labels, or the
  host supplies a label map; the view falls back to nothing rather than to a key.

## The design

### The document contract (Components, `src/core`)

```
DocumentSnapshot(
    string Type, string Key, string Head,
    DocumentDefinition Definition,          // property key → label, value kind, required, read-only, options
    IReadOnlyDictionary<string, string?> Values,
    IReadOnlyList<DocumentRelation> Relations,   // edge key, label, counterpart id, direction
    IReadOnlyList<DocumentAction> Actions)       // transition key, label, input contract

DocumentAction(string Key, string LabelKey, bool Primary, IReadOnlyList<DocumentInput> Inputs)
```

`DocumentView` renders read-only properties through `DataForm.Fields`/`Values`, relations through
`DynamicEdgeForm.ReadOnly`, action buttons with their input contract, a head badge and a
`TransitionResultView` slot for the outcome. It raises an action callback — it does not know how
the action is executed.

### The trigger (Components, `src/lib`)

`TransitionTrigger` is a behavior plus a small component:

- state: `idle | submitting | refused | conflict | applied`, with the last `TransitionResult`;
- it composes the request (`head`, source id, edge key, target type, inputs, property/edge writes)
  and calls the injected `TransitionClient`;
- the host's response updates the document region: **re-render from the returned document**
  (Blazor-native), not an HTML fragment swap (decided 2026-11-26 — the circuit owns the DOM and a
  fragment would drop the component tree, focus and the agent bridge);
- a 409/conflict is surfaced as a case, never silently re-read; a refusal renders as data;
- focus moves to the result region and the outcome is announced, so a keyboard user is not left
  on a stale control.

### The host side (not Components)

- Graph exposes one HTTP transition entry that runs the existing session runner and returns
  `{outcome, cases, document, head}` — the envelope `CPKG0021` renders. Today only the MCP
  `session` tool executes transitions, so this endpoint is the gating dependency.
- The app maps Graph's payloads onto `DocumentSnapshot`, supplies the `TransitionClient`, and
  passes the text resolver.

## Acceptance direction

- `DocumentView`: given a document with declared properties and relations, when it renders, then
  every property appears with its label and value, no key is shown as a label, relations are
  read-only, and the declared actions are offered.
- `DocumentView`: given a pure-read result (no actions), when it renders, then nothing invites an
  edit and no form submits.
- `TransitionTrigger`: given a declared action and its inputs, when a person runs it, then one
  request carries the head and triple, and the response updates the region from the returned
  document rather than a re-read.
- `TransitionTrigger`: given a refusal, a conflict and an invalid input, when each returns, then
  the matching result cases render against the document and the region keeps the current document.
- `TransitionTrigger`: given a keyboard user, when the result arrives, then focus lands on the
  result region and the outcome is announced.
- The full behavior is proven through a browser scenario against an AppBox-style isolated host,
  not only in bUnit.

## Deferred scope

- Server-rendered HTML/CSS fragments for non-Blazor consumers: a projection rendered from the same
  JSON, only when a consumer that needs it exists.
- Offline/replay, edge-commit history, undo, and multi-user live sync.
- Agent bridge wiring (`snapshot`/`act` against the trigger): it consumes the same
  `TransitionClient` once the trigger exists, and is its own scope.

## Evidence and decisions

- **2026-11-26 user decisions:** result cases are structured JSON keyed by stable code (not
  fragments); execution carries the authoritative document and head on applied/refused/conflict;
  validation carries cases and evidence only; wording is client-resolved keys with Graph defaults
  as fallback; fragments deferred; full document rather than a projection; the document is the
  response to the action; re-render from JSON rather than swapping fragments.
- **Delivered prerequisites:** `CPKG0019` (#43), `CPKG0020` (#44), `CPKG0021` (#45) — dynamic form
  fields/values, read-only relation view, and the result-case envelope with its view.
- **Gap this proposal closes:** Graph's app still emits a per-record model so `DataForm` has
  something to reflect, and assembles a record page by hand; `SessionCommandBar` carries a
  session-graph-specific `data-transition-key` with no generic document trigger.
- **Gating dependency:** Graph has no HTTP transition entry (`GET/PUT /api/documents/{id}` are
  read/write only; transitions run through the MCP `session` tool). Handoff
  `20261126T082327906745Z-57c02c4e@components` records the envelope split for `KRNL0048`/`KRNL0051`.
