## Outcome

The document view and the action trigger are observed in a real browser — labels, read-only
values, relations, an action that runs, a refusal, a conflict and the keyboard result — against a
test-owned host with a dedicated Chromium, so focus and announcement are proven rather than
asserted in a unit test.

## Refinement decisions (2026-11-26)

- **The lane's own e2e project and pattern**: `src/e2e` (xUnit v3 + Playwright), a consumer page
  published and started on an ephemeral port through the existing `ConsumerAppHost` helper, and a
  stub `ITransitionClient` compiled into that page. No dependency on AppBox, which is
  backend/harness-owned.
- **The stub is the contract under test**: applied, refused, conflict and invalid are scripted in
  the page's client, so the browser proves the component's behavior, not a live graph.
- **Chromium is the documented dedicated browser** Playwright manages; no user browser is
  attached to.
- **Direct assertions on the DOM**, using the `data-slot`/`data-result-*` attributes the
  components already emit; no screenshot comparison.

## Acceptance criteria

- [ ] UAC01: Given a document in the hosted page, when the browser opens it, then the declared labels and values render and no property key is visible as text.
- [ ] UAC02: Given declared relations and actions, when the page renders, then relations are read-only text and the actions are offered.
- [ ] UAC03: Given the applied stub, when the action is activated, then the region updates to the returned document and the result cases are shown.
- [ ] UAC04: Given the refused stub, when the action is activated, then the refusal case renders and the document shown is unchanged.
- [ ] UAC05: Given the conflict stub, when the action is activated, then the response's document is shown and the retry action is offered.
- [ ] UAC06: Given a keyboard user, when a result arrives, then focus is on the result region and an assistive-technology-visible announcement carries the outcome.
- [ ] UAC07: Given the whole page, when it is inspected, then no page-specific document markup exists outside the components' slots (the page composes the two components only).

## Boundaries

- Browser proof of the components only; the deployed Graph record page is graph's own acceptance
  (`KRNL0031`/`KRNL0056` family), not this scope.
- No live network call is made from the page; the transport stays stubbed.
- No visual regression baseline beyond direct DOM assertions.
