## Outcome

Every script in this repository that shells out to `dotnet` uses a host that can satisfy the
repository's pinned SDK, so Components runs on .NET 10 even when the `dotnet` on `PATH` is a
machine-wide .NET 11 host. When no installed host can satisfy the pin, the script says which
candidates it tried and what to install instead of failing with a misleading message about a
missing application.

## Why the user-scope PATH fix could not work

The repository pins `10.0.100` with `rollForward: latestFeature` in `global.json`. The user's
own `PATH` already begins with the two .NET 10 roots
(`%LOCALAPPDATA%\Microsoft\dotnet`, `%USERPROFILE%\.dotnet`), and the .NET 10 SDK `10.0.404` is
installed there. Windows nevertheless composes a process `PATH` as **machine value followed by
user value**, so the machine entry wins by one position:

| Entry | Position in the composed PATH |
|---|---|
| `C:\Program Files\dotnet\` (host `11.0.100`, plus two empty `sdk\10.0.x` leftovers) | index 26 |
| `%LOCALAPPDATA%\Microsoft\dotnet` (host `10.0.404`) | index 27 |

`where.exe dotnet` therefore returns the Program Files host first, that host cannot satisfy the
pin, and everything that spawns `dotnet` failed — the packaging scenarios, the trim probes and
`eng/build-local.ps1`. Reordering *user* PATH entries cannot change that ordering.

## What changes

| Surface | Change |
|---|---|
| `eng/dotnet-host.ps1` (new) | `Resolve-DotnetHost -RepositoryRoot` probes the host under `DOTNET_ROOT` and then the plain command from `PATH`, from the repository root so `global.json` applies, and returns the first that reports a version; when none does it throws one diagnostic naming each candidate and its observed state |
| `eng/build-local.ps1` | builds and packs through the resolved host |
| `src/test/CPKG0001.Packaging/consumer-scenario.ps1` | resolves the host once, as soon as the repository root is known, and uses it for the runtime listing and every restore, build, pack and publish step |
| `src/test/CPLG0001.Integration/US01.PluginManifest/feature-scenario.ps1` | same, for its pack step |
| the three trim probes (`CTRM0001`, `CPKG0006`, `CPKG0007`) | same, for their publish, restore and workload calls |

## Acceptance

- [x] UAC01: Given a `PATH` whose `dotnet` cannot satisfy the pinned SDK, when a script resolves its host, then it selects an installed host that can, and the work it performs succeeds.
- [x] UAC02: Given no installed host that satisfies the pin, when a script resolves its host, then it refuses with one diagnostic that names every candidate it tried, the state it observed and the action to take.
- [x] UAC03: Given the resolved host, when the whole suite runs with the non-satisfying host first on `PATH`, then every test passes with no skips.
- [x] UAC04: Given the lane's scripts, when they are inspected, then none invokes `dotnet` except through the resolver.

## Boundaries

- This changes the lane's own scripts only: no project target framework, no package code, no
  published contract, and no machine-wide PATH entry. The SDK pin itself was already committed
  (`0842855d`) and stays as it is.
- A machine-wide remedy — removing the machine `dotnet` entry or installing a .NET 10 SDK into
  the machine root — remains available and is the user's decision; this scope removes the
  lane's dependence on it either way.

The first hostile-PATH attempt was red (22 failures) and exposed two defects in this repair
itself, both fixed before the green run: a `Select-Object -First 1` on the probe pipeline
ended the host early and made its exit code read as failure, and one replacement swallowed the
`$dotnetHost` variable at the runtime listing.
